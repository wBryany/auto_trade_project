# listenKey 续期恢复后重复告警（2026-09-10）

## 发生了什么

00:11:18 的邮件重复报告的是 9 月 9 日 22:38 的旧错误，并非当时产生
了新的 HTTP 429。部署日志 `dashboard.restart.20260909-213832.stderr.log`
记录了连续的完整 HTTP 请求序号，可以区分实际请求与页面重复读取。

| 时间（CST） | 实际事件 |
| --- | --- |
| 9/9 22:38:53.549 | `PUT /fapi/v1/listenKey` 唯一一次真实 429；IP 权重 2791，截止 22:38:58.549 |
| 9/9 22:39:19.243 | 第一封限频邮件，当时续期尚未确认恢复 |
| 9/9 22:39:54.330 | 下一次续期成功，HTTP 200 |
| 9/9 23:09:54.897 | 续期成功，HTTP 200 |
| 9/9 23:39:56.247 | 续期成功，HTTP 200 |
| 9/10 00:09:56.644 | 续期成功，HTTP 200，IP 权重 897 |
| 9/10 00:11:18–19 | 页面再次读取旧错误，发送第四封告警；没有新的 HTTP 429 |

后面三封重复告警分别在 23:09、23:40、00:11 发出，与通知器的
1800 秒冷却周期吻合。冷却机制本身并未失效：续期成功后只更新了
`_last_keepalive_at`，没有清除 `_last_error`、`_last_exception` 和旧截止。
页面于是一直把已经恢复的故障当作当前故障。

部署至 00:15 累计 24 次真实 REST 请求：18 次启动及历史初始化、
6 次续期（5 次成功、1 次失败）。9 月 10 日零点至检查时只有 00:09
这一条成功续期。当初真实 429 发生的滚动 60 秒内，本进程仅发出
1 个请求，因此不能将出口 2791 权重归因于这个进程的高频轮询。

## 修复原则

- 给私有流错误区分来源和版本。只有同一订阅、同一故障版本的续期
  明确成功，且没有更新故障或未来等待截止时，才清除对应续期故障。
- 不能因为 WebSocket 心跳正常或等待时间到期，就宣称 REST 已恢复。
  并发发生的 bootstrap、传输或订阅失效故障不能被旧续期响应清除。
- 明确成功的 REST 恢复向状态页提供证据。页面在账户健康且没有其他
  当前错误时结束旧告警事件，让下一次真实故障立即进入通知流程。
  每次恢复有唯一凭据，仅消费一次；新错误或全局 HTTP 冷却会作废
  同快照携带的旧凭据，避免用过去的成功清除后来的故障。
- 保留真实 429/418 的等待机制和应急通知，不通过延长冷却、关邮件或
  忽略所有健康 WebSocket 上的 REST 错误来掩盖问题。

测试使用模拟网络与时钟验证失败→成功→跨 30 分钟无重复通知，以及
恢复后新故障立即告警；另覆盖错误并发、换 key、停止、未来截止和
没有明确 REST 恢复证据的情况。测试不向交易所请求、不发送真实邮件。

网络故障后三类成功续期都能准确复现旧错误残留，修复后均通过。
